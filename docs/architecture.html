01 — Product

What BPZILLA Is

A searchable archive of genuine Nissan factory production records, decoded from original FAST parts-catalogue microfiche and served as a static site that runs entirely in the visitor's browser.

Every row in BPZILLA came off a Nissan FAST disc — the same parts-catalogue system a Nissan dealer's counter used. It is not a community-compiled spreadsheet, not scraped from auction listings, and not estimated from production totals. That distinction is the product: it is the reason a number here can be cited.

The archive covers 1,253,580 build records across 30 chassis (34 data files, six of which are the Z32 export markets merged into two), presented as 35 browsable models. For any given car it answers three questions: what exactly did the factory build, how many were built like it, and how do we know.

What the site does

  • VIN Archive — search and filter the full record set by chassis number, paint, grade, year, series or transmission.
  • Plate Decoder — paste a chassis number and get the build plate read back field by field, with each factory option named.
  • Stats & Rarity — per-model breakdowns and a grade-by-paint production matrix.
  • Rarity Calculator — the exact number of cars built to a chosen grade, paint and option combination.
  • History & Legends — editorial context for the Skyline line and the non-Skyline chassis (Silvia, 180SX, Stagea, 300ZX).
Design principle

The archive never fills a gap with a plausible guess. Where a code's meaning is not confirmed, the site shows the raw code and says it is undecoded. Every count that appears as a number is counted from records, not modelled from proportions — a rule this codebase has had to be corrected against more than once.

02 — System

System Architecture

BPZILLA is a static site with no database server and no API. The entire archive is shipped to the browser as compressed JSON on first load and queried in memory from then on. There is nothing to scale, nothing to keep running, and no request path that can be slow for one visitor and fast for another.

One piece of server-side logic exists: a Worker script that runs ahead of static-asset serving for /data/ and refuses requests that don't carry a same-origin signal. Everything else — the page, the styles, the scripts, the images — is served straight from the edge without the script running at all. See Bulk-copy protection.

03 — Ingest

Data Pipeline

The source is a set of Nissan FAST discs held locally: H:\AR-JP\JP holds 196 numbered Japanese-market model directories, and H:\NISSAN\{US,CA,EL,ER,GL,GR} hold the export-market equivalents. These are binary microfiche exports in Shift-JIS (CP932), not documents.

Extraction scripts

Two committed extractors regenerate the derived data files. Both are deterministic and re-runnable against the discs.

ScriptOutputWhat it does
extract_fastop.ps1 factoryOptions.json Parses FASTOP's 63-byte records, merges continuations, decodes Shift-JIS and translates with a longest-first phrase map. Throws if any untranslated non-ASCII residue survives, so a silent half-translation cannot ship. Produces 462 definitions (R33 258, R34 58, S14 70, WC34 76).

Record file shape

// public/data/fast_<chassis>.json — dictionary-encoded, one file per chassis { "m": "BNR34", // chassis id "n": 11474, // record count "b": ["0","1", ...], // series block dictionary "d": ["1999-01", ...], // build date dictionary "c": ["QM1","TV2", ...], // colour field dictionary (trim char + paint code) "t": ["5", ...], // interior/trim dictionary "mc": ["GJPRWYR34ZDA...", ...],// factory model code dictionary "r": [[blk, ser, di, ci, ti, mci], ...] // rows as dictionary indices }

Export-market Z32 files carry two extra keys: vin, a reconstructed per-record VIN, and exportInfo, which records how many of those VINs pass NHTSA check-digit validation.

04 — Storage

Data Model

A record-per-object model at this scale costs hundreds of megabytes in the browser. Instead each chassis is held as a set of parallel typed arrays, with every repeated string interned once per file. Record objects are materialised only for rows actually displayed.

// in-memory column, one per physical chassis file { n: 11474, // rows blk: Uint8Array, // series block -> dict.b ser: Int32Array, // serial number (the real integer) di: Uint16Array, // build date -> dict.d ci: Uint16Array, // paint code -> dict.c | trim char -> dict.ctr ti: Uint8Array, // interior -> dict.t mci: Uint16Array, // model code -> dict.mc dict: { b, d, c, ctr, t, mc }, ranges: { blockIdx: [firstRow, lastRow] } // for binary search }

The colour field split

A Nissan build plate records body colour as a three-character exterior paint code preceded by a one-character interior trim code. On the older JDM discs that trim character is often blank, which is why the same paint arrives as KH3 on some records and GKH3 on others.

At load, _splitColorDict separates them once at the dictionary level: dict.c becomes the paint code and dict.ctr the trim character at the same index. Nothing is discarded and no per-record storage is added, and every consumer — breakdowns, filters, matrix, rarity, search — is corrected at the same time.

Why KPS13 is the exception

Whether two split models share a chassis prefix is decidable from the data, not a matter of opinion. If they share one factory numbering sequence their serials are disjoint; if they are separate sequences the serials collide. Measured across all five splits: ER34, RS13, WGNC34 and ECR33 overlap on 0% of records — one sequence each, so sharing the prefix is correct. PS13/KPS13 overlap on 99.90% — 12,185 of KPS13's 12,197 records — so they are two sequences and must be stamped separately.

Chassis lookup

Rows are stored sorted by series block then serial, so a chassis number resolves by binary search inside that block's recorded span rather than a lookup map. Two guards matter: files that arrive out of order are sorted at load and their ranges rebuilt, and the search walks out across equal serials, because one file holding two numbering sequences can legitimately contain the same serial twice.

05 — Interpretation

Decode Reference

The factory model code — the mc field, twenty characters like GJPRWYR34ZDA--L--R34 — is where grade, transmission and factory options are read from.

Critical alignment fact

A real build plate's MODEL string carries one extra leading body-style character that the FAST mc export drops. Published per-position plate decodes therefore map onto this data at exactly −1. This offset is confirmed against photographed plates for BNR32, BCNR33, BNR34 and ER34. Getting it wrong shifts every option by one field.

06 — Method

Provenance & Verification

The archive's value rests entirely on the discipline behind what it is willing to claim. These are the working rules.

Source hierarchy

  1. The FAST discs themselves. Nissan's own tables beat any secondary source, because they are per-disc, era-correct and match the exact codes present in the records.
  2. Independently published production figures. Used to validate a decode, never to generate one.
  3. Corroborated community sources. Two or more independent published sources in agreement, and only where the archive's own data supports the claim.

Worked example — naming paint code 1N3

No disc in the set names 1N3. Owner-forum sources describe it as a two-tone finish limited to Series 1 R33 GTS cars. That alone would be weak. But every one of the 5,485 1N3 records in the archive falls between 1993-02 and 1994-11 — precisely the Series 1 window — which is independent corroboration from a source the forums had no access to. It is named on that basis and flagged as lower-confidence below.

Rules the project holds to

  • Never name a letter off a coincidence. A "Type G" decode was rejected because the real Type G is roughly 850 units while the candidate letter covered 65–100% of the model.
  • Retract on discovery. A Z32 "Version S" decode was shipped and then withdrawn: Version S launched October 1994, but the letter appears from 1989. The code now returns nothing and carries a comment explaining why.
  • Date boundaries are evidence. A running change that starts or stops cleanly is real; a letter smeared across the whole production run is not a variant.
  • Undecoded is a legitimate answer and is shown as one, rather than being hidden by dropping the rows.

Overrides are applied conservatively. 07 — Quality

Audit Report

A full sweep of all 39 models and 1,284,067 records, plus a layout pass at four viewport widths, run 21 August 2026. Eight defects found and fixed. Every finding below was verified against the data before being treated as a bug, and the fixes were verified after.

These sweep figures are left exactly as measured on the day. They predate the removal of the M35 Stagea on 22 August 2026, which is why they count 39 models and 1,284,067 records against the 35 and 1,253,580 stated above. The M35 data files were not deleted, only unloaded.

Rarity figures were modelled, not counted

CriticalFixed

The rarity calculator multiplied grade share by colour share by a table of invented per-option coefficients — cold weather 0.18, leather 0.08, and so on, numbers with no source behind them. The result was printed onto a "Certificate of Authenticity" as though counted.

BNR34 V-Spec II Nür in Bayside Blue (TV2) reported 1 of 178 actual 1 of 119 (grade x colour cross-tab) error +50%

Fix: the combination is now counted directly from the loaded records, verified against a brute-force pass over 108 grade/colour pairs with zero disagreement. The option checkboxes are built from each chassis's own decoded build plates, so every box offered is something the archive can really count. A combination that was never built now reports zero rather than being rounded up to one.

KPS13 records carried duplicate chassis numbers and could not be found

CriticalFixed

KPS13's 12,197 records were stamped with PS13's chassis prefix. Because the two run separate factory numbering sequences, this generated 12,185 chassis numbers that collided with real PS13 cars — and not one KPS13 record could be retrieved by its own displayed identifier.

serial overlap between split siblings ER34_GT / ER34_GTT 0.00% -> one sequence, share prefix RS13 / KRS13 0.00% -> one sequence, share prefix WGNC34 / WGNC34_260RS 0.00% -> one sequence, share prefix ECR33 / ECR33_V 0.00% -> one sequence, share prefix PS13 / KPS13 99.90% -> two sequences, must differ

Fix: KPS13 now carries its own stamped prefix, matching the E-KPS13 type designation already recorded against it. Lookup and search resolve the stamp rather than the file id.

Colour codes were read whole, fragmenting every paint

HighFixed

The colour field is a trim character plus a paint code, but was being treated as one opaque string. One paint therefore counted as several, and every per-colour count, percentage and rarity denominator was computed against a fragment of the true total.

colours displayed vs. real paints NM35 Stagea 33 -> 10 GCZ32 42 -> 25 Z32 31 -> 22 S13 23 -> 14 WGC34 22 -> 14 records showing a raw code instead of a name before 612,424 (48% of the archive) after 51 (0.004%)

Fix: the field is split once at dictionary level, correcting all consumers together. The trim character is preserved and shown as its own field, so the full plate string is still visible.

The paint table covered a fraction of the archive

HighFixed

75 hand-maintained names against 98 codes actually in use, and several were wrong or era-mismatched. TV2 — Bayside Blue, the single most recognisable colour in the archive — read simply "Blue".

Fix: paint.json is now generated from Nissan's own colour master on the discs, giving 117 names and 100.00% record coverage. A small curated layer supplies established marketing names where two independent sources agree.

PS13 broke the sort invariant chassis lookup depends on

HighFixed

Lookup binary-searches within a block's recorded row span, which is only valid while rows are grouped by block and ascending by serial. In PS13 the KPS13 rows sit after the block-1 rows as a second block-0 run, so block 0's span covered the entire file and the serials inside it were not monotonic.

PS13 col.ranges["0"] = [0, 112311] spans all 112,312 rows foreign rows inside span 1,350 non-monotonic steps 2 all 33 other chassis files clean

Fix: files arriving out of order are sorted at load and their ranges rebuilt. Verified by 2,700 randomised round-trips across the affected models with zero failures.

Breakdowns silently dropped rows they could not decode

MediumFixed

Grade and transmission breakdowns skipped any record whose code did not decode, so their percentages summed to less than 100% and the rows did not reconcile against the model total — 54 records on S14, 40 on PS13, 11 on S13, 2 on BNR32, and 65% of ER33's transmission column.

Fix: undecodable rows get a labelled "Not decoded" bucket. The wording is deliberate — ER33 records do carry a value at that position (a literal N on early production); we simply cannot say what it meant, and claiming the plate was blank would be a different and wrong statement.

A full chassis number returned near-misses

MediumFixed

Substring matching meant searching BNR34-000101 also returned BNR34-001010 through -001019, whose dash-stripped forms contain the query.

Fix: an exact hit answers with that car alone; partial queries keep matching as before. Two results can still be correct — the same serial in two series blocks is two different cars.

Content was being clipped off the side of every view on a phone

HighFixed

Because body sets overflow-x: hidden, none of this produced a scrollbar — it was cut off silently, which is why a data-layer audit never surfaced it.

The header failed on all six views. The title was capped at 46vw, reserving 172px of a 375px screen, but the avatar, plate badge and two gaps had already spent 208px of the 343px available. The brand row came to 388px, so the avatar's left edge and the end of the title were both cut.

Four more elements failed for the same underlying reason — a min-content floor that a container could not shrink below:

element demanded available <select> (longest option) 384px 351px rarity calculator .filter-select 303px 272px filter bar .decoder-key-head > div 320px 250px hard-coded min-width .footer-links (6, nowrap) 350px 272px no wrapping

Fix: min-width: 0 where flex and grid items need to shrink, minmax(0, 1fr) instead of bare 1fr tracks, and wrapping on the footer. The viewport-percentage guess in the header is gone — letting the flex items shrink sizes it correctly at any width, and the ellipsis falls wherever the screen really ends.

Also raised in the same pass: nav tabs from 37px to 44px, form controls to 42px, build-plate position numbers from 8.7px to 10.2px, and the rarity option checkboxes from 13px to 17px with a 50px padded row as the tap target.

One of these was self-inflicted: spelling paint names out in full is what pushed the <select> minimum to 384px, so the colour work earlier the same day caused the calculator overflow.

Checked and found correct

Two things that looked like defects were verified as deliberate and left alone.

  • R31 and R30 are not loaded. fast_hr31.json (182,351 records) and fast_dr30.json (44,439) sit in the data directory but are absent from the loader. Both counts were verified against the FAST source; they are out of scope by request, not a loading bug.
  • ER33's undecoded transmission is honest. All 18,539 affected records carry N, and they stop cleanly at 1995-12 while F/A coverage ramps up — the signature of a field that only began being populated properly, not a third gearbox.
  • The certificate watermark only looked like it was escaping. It measures 521px wide inside a 244px card, but .certificate-inner already clips it — a bounding box reports its layout size regardless of ancestor clipping. No fix applied.

08 — Candour

Known Limits & Open Questions

Published deliberately. A reader who knows where the archive stops can trust the rest of it.

Open decode questions

QuestionScaleStatus
Colour-field trim character — the letters G C Z J S E B that precede the paint code. ~400k records Structure confirmed from Nissan's own colour master and an independent source describing the plate as paint code plus one interior trim character. The individual letters are not named anywhere on the discs, so they are shown raw.
ER33/ECR33 N at the transmission position. 20,455 records Real running-change boundary (1993-02 to 1995-12) but meaning unconfirmed. Reported as not decoded.
Eight paint codes with no factory name — 3W9 2R8 3N1 EM3 5G9 125 4J1 6G1. 51 records Absent from every description table on every disc. Shown as the raw code.
1N3 / 1N4 naming — R33 two-tones. 28,730 records Named from corroborated community sources plus internal date-span evidence, not from a disc. Lower confidence than every other name in the table.
Z32 grade split. 162,666 records No clean signal found. A previous "Version S" decode was retracted.
Option blocks for R32, S13 and Z32. — These chassis predate the FASTOP definition table, so there is no authority to decode against.

Data limitations

  • Export Z32 build dates are year-only (1990 rather than 1990-05). This is the granularity of the source, not a parsing loss.
  • Export identifiers vary in confidence. US and Canada VINs are independently NHTSA check-digit validated; the EL and ER destination codes are inferred from third-party parts-catalogue listings and are not confirmed inside the dataset. Each record states which it is.
  • Body style is not recoverable per record — coupe versus sedan would need a VINDAT→MDLCODE chain that is not yet built.
  • Survival is not modelled. Everything here is production, not how many still exist.

Technical debt

  • No CSP. Deliberate — two CDN scripts and inline styles throughout mean any policy strict enough to be worthwhile would need unsafe-inline. Revisit if the CDN dependencies are vendored.
  • Two external CDNs with no fallback — the site's main availability risk.
  • The archive can still be copied by anyone willing to target it. The /data/ gate stops stock tooling, not a spoofed header or a headless browser. Closing it properly means not shipping the corpus — see Bulk-copy protection.
  • Tabs do not survive a refresh and cannot be linked to; hash-based routing is not implemented.
  • Whole-archive queries are linear scans. Fine at 1.28 M rows in a typed array; would need indexing well before 10 M.

Bulk-copy protection

The record files are the site's substance, and until this was added they were a public bulk download: curl https://bpzilla.com/data/fast_hcr32.json returned 144,097 records in 0.41 seconds with no browser, no referer and no session. Forty such requests is the entire archive in a few seconds. robots.txt disallows /data/, but robots.txt is a request rather than a control, and the crawlers worth worrying about are the ones that ignore it.

src/index.js now runs ahead of asset serving for /data/ and refuses anything without a same-origin signal — Sec-Fetch-Site: same-origin, a same-origin Referer, or a matching Origin. Any one of the three is accepted, because none is universal: Sec-Fetch-Site is absent before Safari 16.4, and Referer can be stripped by a privacy extension.

What this does and does not do

It does not make the data uncopyable, and nothing at this layer can. The archive is queried in the visitor's browser, so the browser must receive all of it — and anything a browser can receive, a headless browser can receive too.

It also does not resist a targeted scraper: a single spoofed header defeats it. Verified — curl -H 'Referer: https://bpzilla.com/' passes.

What it removes is the free option. Generic crawlers, wget, python-requests, archivers and AI scrapers using stock HTTP libraries all send none of these headers and are refused. Copying the archive stops being one shell command and starts requiring someone to deliberately target this site — which is also the point at which edge rate limiting starts to bite, because that is IP- and behaviour-based and does not care what headers are sent.

Rate limiting

The gate is defeated by a spoofed header; a per-address limit isn't. Cloudflare's rate-limiting binding is declared in wrangler.jsonc and enforced in the same script, so it lives in the repository rather than in dashboard state nobody can review. 300 requests per minute per IP — far above real use, since a visitor pulls 40 files once per page load, leaving room for roughly seven full reloads a minute. It runs after the origin check, so a request that was never going to be served doesn't spend a limit call on the way out, and it fails open: a missing binding or a throw allows the request, because a rate limiter having a bad day must never be why the archive stops loading.

Local development
